# references/restart-strategy.md

## 质疑后重启策略

**文档描述**  
本文档定义 DebugFixer 在完成方向自疑后，如何根据质疑的分层结果，选择正确的重启策略。它是连接“质疑”与“下一轮行动”的桥梁，确保 AI 不会在方向自疑后茫然无措或粗暴地全盘推倒重来，同时在重启中保持对状态的自我验证，避免重复错误。

**核心目标**  
- 根据质疑层级（信号层/理解层/系统层）提供差异化的重启路径。  
- 最大化保留有效分析成果，最小化重复工作。  
- 引入重启验证机制，防止保留的资产与新事实矛盾。  
- 设定系统层重启上限与退出机制，避免无限循环。  
- 在重大重启前征得用户确认，保护协作体验。

---

### 核心原则

1. **区分层级，按级重启**  
   不同层级的质疑意味着当前分析框架的可信度受损程度不同。重启力度应与质疑层级匹配，从“补全信息”到“调整假设”再到“完全重建”，逐步升级。

2. **保留有效资产**  
   调用链结构、环境缓存（`.debug/config.yaml`）、已有的埋点日志（Proceed 后仍可能存在）应尽可能保留，除非它们本身已被质疑推翻。

3. **重启后必须验证资产一致性**  
   执行任何层级重启后，AI 必须立即检查保留的资产（调用链、环境缓存、保留的假设）是否与用户新补充的信息或新理解一致。若存在矛盾，应升级重启层级（信号层升级为理解层，理解层升级为系统层），并重新输出升级后的重启清单。

4. **系统层重启设上限**  
   系统层重启最多执行 **1 次**。若系统层重启后仍然无法修复并再次触发方向自疑，AI 不应再次重启，而应输出最终建议并退出，生成 `FAIL-FINAL-<标题>.md`。

5. **系统层重启需用户确认**  
   系统层重启意味着之前所有分析工作基本作废。在输出重启清单后，AI 必须明确询问用户是否同意推倒重来，不能单方面执行。

6. **不重复同样的错误**  
   被质疑推翻的正确性假设必须明确标记为废弃，并在重新建立的假设中避免同样的误解。

7. **重启即新一轮飞轮**  
   重启后，应严格按照 SKILL.md 定义的工作流从对应步骤重新开始（如静态分析或埋点计划），不跳步。

---

### 分层重启策略

#### 第一级：信号层质疑通过后的重启（补全信息）

**适用场景**：质疑仅涉及上下文缺失、环境差异等可通过用户补充信息解决的问题。系统理解和假设没有根本错误，只是输入信息不足。

**重启动作**：
1. **等待用户回复**：用户在方向质疑的追问中提供了补充信息（如环境变量、复现前置步骤等）。
2. **更新上下文**：将用户补充的信息纳入评估。
3. **执行重启验证**（见后文）。
4. **继续当前飞轮**：**不重新开始静态分析**。在现有调用链和假设的基础上，调整或补充埋点计划。
5. **可选**：如果需要验证新提供的信息，可在下一轮埋点中增加 1~2 个针对性位置。
6. **返回流程**：直接回到 SKILL.md 步骤 4（分层埋点计划），使用当前的 `session_id`。

#### 第二级：理解层质疑通过后的重启（调整假设）

**适用场景**：质疑表明正确性假设可能存在根本性错误，或修复路径存在误判，但调用链结构和环境判定仍然可靠。

**重启动作**：
1. **废弃被质疑的假设**：将之前所有与质疑结果矛盾的假设标记为“废弃”或降低至“低”。
2. **重新建立假设**：基于已有的调用链和用户补充信息，重新调用 `references/correctness-hypothesis.md` 建立新假设。
3. **重置怀疑度**：基于新假设重新评估嫌疑点排序。
4. **执行重启验证**。
5. **保留调用链**：调用链结构通常无需改动。
6. **返回流程**：回到步骤 4（分层埋点计划），使用原 `session_id`，重新制定首轮 ≤3 处埋点计划。

#### 第三级：系统层质疑通过后的重启（完全重启）

**适用场景**：质疑涉及架构级缺陷、多 Bug 交织或设计层面的根本问题，表明当前整个分析框架可能失效，局部修复无意义。

**重启动作**：
1. **用户确认**：在输出重启清单后，追加明确询问：
   > “系统层重启意味着之前 3 轮的分析工作将基本作废，重新开始。预计需要额外 2~3 轮对话。是否继续？还是先尝试其他方向？”
   若用户选择 **Proceed**，则继续执行；若用户选择 **Mark Fixed** 或提供其他方向，则按用户决策执行。
2. **清空当前会话**：生成新的 `session_id`（旧 session 的日志可选择保留或归档）。
3. **保留环境缓存**：`.debug/config.yaml` 通常仍有效，保留。
4. **完全重新静态分析**：读取所有涉及文件，重新梳理调用链（即使之前已梳理过，也要带着新的理解重新审视）。
5. **重建正确性假设**：从头建立，不参考任何之前废弃的假设。
6. **重新评估复杂度**：可能因架构问题发现而上升。
7. **执行重启验证**。
8. **返回流程**：从步骤 2 重新开始，但应向用户说明为何需要完全重启。
9. **若系统层重启后再次触发方向自疑**，不执行第二次系统层重启。转而进入 **5. 退出与最终建议** 流程。

---

### 重启验证

在任何层级的重启动作执行完毕后，**必须执行以下检查**，防止保留的资产与新事实冲突：

| 检查项 | 若“是”的处理 |
|--------|--------------|
| 保留的调用链是否与用户新补充的信息矛盾？（如用户指出某个函数从未被调用） | 升级为**理解层重启**：废弃当前调用链，重新梳理。若调用链废弃后也影响假设，则升级为**系统层重启**。 |
| 保留的正确性假设是否与用户新确认的业务规则矛盾？ | 升级为**理解层重启**：废弃矛盾假设，重新建立。 |
| 环境缓存 (`.debug/config.yaml`) 是否与用户提供的环境信息矛盾？（如用户说该文件运行在客户端，但缓存标记为服务端） | 修正环境缓存，按新环境选择模板继续。不升级层级。 |
| 新事实是否指向更根本的架构问题？ | 直接升级为**系统层重启**，并向用户说明原因。 |

**若升级到系统层且已执行过一次系统层重启**，则不执行新的系统层重启，进入退出流程。

---

### 退出与最终建议

当满足以下任一条件时，AI 应终止重启循环，输出最终建议：

- 系统层重启已执行过 1 次，再次触发方向自疑。  
- 用户明确拒绝系统层重启。

**执行动作**：
1. 输出 **【最终建议】** 段落：
   ```
   【最终建议】
   DebugFixer 已尝试三轮飞轮、方向自疑及一次系统层重启，仍无法在可分析范围内定位问题根因。
   建议：
   - 将问题拆分为多个独立缺陷，逐一隔离测试。
   - 引入更高级的调试工具（分布式追踪、内存分析、并发压测）。
   - 进行人工架构评审，评估是否存在设计缺陷需要重构。
   ```
2. 生成 `FAIL-FINAL-<修复标题>.md`，完整记录所有分析过程、质疑内容和最终建议。
3. 调用 `AskUserQuestion: Mark Fixed / Proceed`，允许用户选择结束或手工引导新方向。

### 重启清单输出模板

```
【质疑后重启清单】
- 重启层级：信号层 / 理解层 / 系统层
- 用户确认：（系统层必填）是否已征求用户同意？
- 保留：调用链结构、环境缓存 (.debug/config.yaml)、当前日志
- 废弃：假设 A、假设 B（标记为低置信度）
- 重新建立：正确性假设（基于补充信息 / 新理解）
- 返回步骤：步骤 4 / 步骤 2
- 是否新 session_id：是 / 否
- 重启验证结果：（执行后填写）
- 具体执行指引：继续当前飞轮，调整假设后重新埋点 / 完全重启分析
```

### 示例

**场景 1：信号层重启**

```
【质疑后重启清单】
- 重启层级：信号层
- 用户确认：不适用
- 保留：调用链结构、环境缓存
- 废弃：无
- 重新建立：无
- 返回步骤：步骤 4
- 是否新 session_id：否
- 重启验证结果：通过，用户补充的 Node.js 版本与保留的调用链无冲突。
- 具体执行指引：继续当前飞轮，在 checkout 入口增加环境标识埋点。
```

**场景 2：理解层重启**

```
【质疑后重启清单】
- 重启层级：理解层
- 用户确认：不适用
- 保留：调用链结构、环境缓存
- 废弃：假设“getCart 必定返回非 null”（标记为低置信度）
- 重新建立：正确性假设——“getCart 对未登录用户可能返回 null，调用方需处理”
- 返回步骤：步骤 4
- 是否新 session_id：否
- 重启验证结果：新假设与调用链一致，无需升级。
- 具体执行指引：基于新假设重新评估怀疑度，首轮埋点计划集中在 handleRequest 对空 cart 的处理。
```

**场景 3：系统层重启（含用户确认）**

```
【质疑后重启清单】
- 重启层级：系统层
- 用户确认：已向用户说明“系统层重启意味着之前 3 轮的分析基本作废，重新开始。预计额外 2~3 轮对话。”用户选择 Proceed。
- 保留：环境缓存
- 废弃：之前所有假设及调用链分析
- 重新建立：全部正确性假设，重新梳理调用链（需包含跨服务边界）
- 返回步骤：步骤 2
- 是否新 session_id：是（旧 session 归档为 sess_xxx_failed）
- 重启验证结果：待执行后填写。
- 具体执行指引：完全重启，从静态分析开始，明确跨服务的责任边界。
```

**场景 4：退出与最终建议**

```
【最终建议】
DebugFixer 已尝试三轮飞轮、方向自疑及一次系统层重启，仍无法在可分析范围内定位问题根因。
建议：
- 将优惠券服务拆分为规则引擎和优惠计算两个单元，分别单元测试。
- 引入分布式追踪查看优惠券计算全链路。
- 人工评审是否有隐式的线程不安全访问。
→ AskUserQuestion: Mark Fixed / Proceed
```

### 与其它参考文档的协同

- **方向自疑**：本文件由 `direction-doubt.md` 在输出重启清单时引用。  
- **正确性假设**：理解层和系统层重启时需重新调用 `correctness-hypothesis.md`。  
- **埋点体系**：重启后依然遵循 `instrumentation-guide.md` 的分层验证策略。  
- **记忆系统**：退出生成的 `FAIL-FINAL` 文档由 `memory-system.md` 管理。

---

**使用提示**：重启是理智调整，不是失败。永远记录重启原因与保留资产，并在重启后第一时间验证一致性。面对系统层推倒重来，尊重用户的决策权。当连重启本身都失效时，勇敢地承认边界，给出建设性的退出建议——这是 DebugFixer 作为一个真正可信赖搭档的最终担当。

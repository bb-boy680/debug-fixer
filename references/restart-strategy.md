# 质疑后重启策略

## 文档描述

本文档定义 debug-fixer 在完成方向自疑后，如何根据质疑的分层结果选择正确的重启策略。

它是"质疑"与"下一轮行动"之间的桥梁，确保不会在方向自疑后盲目全盘推倒重来，也不在需要重建时抱着已证伪的假设不放。

本文档承接 `direction-doubt.md` 的【质疑后重启清单】，输出分层重启动作供 README 流程中的【方向重启】执行。

---

## 核心原则

1. **分层重启，按级匹配**：质疑层级 == 重启力度。信号层补全信息、理解层调整假设、系统层完全重建。
2. **保留有效资产**：调用链结构、环境缓存、已有埋点日志应尽可能保留，除非被质疑推翻。
3. **重启后验证一致性**：执行重启后必须检查保留资产与新事实是否一致，矛盾则升级重启层级。
4. **系统层重启限一次**：系统层重启最多 1 次。再次触发方向自疑 → 不重启，输出最终建议退出。
5. **系统层重启需用户确认**：明确告知用户分析工作基本作废，不得单方面执行。
6. **重启即新一轮循环**：重启后从 README 流程对应步骤重新开始，不跳步。

---

## 禁止行为

- **禁止在信号层问题未排除时直接做系统层重启**：先补全信息，再看是否需要升级。
- **禁止不清算旧的正确性假设**：被质疑推翻的假设必须显式标记为废弃。
- **禁止跳过重启验证**：任何层级重启后必须执行验证表检查，不做则可能造成错误叠加。
- **禁止执行第二次系统层重启**：一次系统层重启后仍失败 → 直接走退出流程。

---

## 分层重启策略

### 第一级：信号层（补全信息）

**适用**：质疑仅涉及上下文缺失、环境差异等可通过用户补充解决的问题。

**动作**：
1. 等待用户回复补充信息
2. 更新上下文，执行重启验证
3. 继续当前埋点分析，不重新做静态分析
4. 可选：增加 1~2 处针对性埋点验证新信息
5. 回 README【埋点分析】

### 第二级：理解层（调整假设）

**适用**：正确性假设存在根本性错误或修复路径误判，但调用链和缓存仍可靠。

**动作**：
1. 废弃被质疑推翻的假设（标记为低置信度）
2. 基于已有调用链和用户补充信息重新建立假设
3. 重置怀疑度排序，执行重启验证
4. 保留调用链和环境缓存
5. 回 README【埋点分析】，重新制定首轮 ≤3 处埋点

### 第三级：系统层（完全重启）

**适用**：架构级缺陷、多 Bug 交织或设计层面根本问题，局部修复无意义。

**动作**：
1. 向用户确认："系统层重启意味着之前分析基本作废，预计额外 2~3 轮对话。是否继续？"
2. 保留环境缓存，其余重新来过
3. 从头静态分析、重建调用链和假设
4. 回 README【多维分析】重新开始
5. 若系统层重启后再次触发方向自疑 → 不执行第二次，走退出流程

---

## 重启验证

任何层级重启后必须逐项检查：

| 检查项 | 不通过的处理 |
|--------|-------------|
| 保留的调用链是否与新信息矛盾？ | 升级为**理解层重启** |
| 保留的假设是否与新确认的业务规则矛盾？ | 升级为**理解层重启** |
| 环境缓存是否与新环境信息矛盾？ | 修正缓存，不升级层级 |
| 新事实是否指向更根本的架构问题？ | 升级为**系统层重启** |

若升级到系统层且已执行过一次系统层重启，不执行，走退出流程。

---

## 退出与最终建议

以下条件触发退出：

- 系统层重启已执行 1 次，再次触发方向自疑
- 用户明确拒绝系统层重启

**动作**：
1. 输出最终建议：建议拆分缺陷隔离测试、引入更高级调试工具、或进行架构评审
2. 记录未能定位根因的模块和已排除方向，作为当前 session 负向约束
3. 调用 `AskUserQuestion: Mark Fixed / Proceed`

## 与其它参考文档的协同

- 方向自疑：由 `direction-doubt.md` 在输出重启清单时引用
- 埋点体系：重启后仍遵循 `instrumentation-guide.md`
- 根因追溯：系统层重启后重新执行 `root-cause-tracing.md`

# references/memory-system.md

## 记忆库与学习系统

**文档描述**  
本文档定义 DebugFixer 的记忆库系统，它如何记录每次修复的成功经验与失败教训，以及如何在新 Bug 分析时检索并引用历史案例。记忆库是 DebugFixer “越用越强” 的核心驱动力。

**核心目标**  
- 将每次修复（成功或失败）沉淀为轻量、脱敏的 Markdown 文档，供后续复用。  
- 支持按标题关键词和元数据快速检索相关案例。  
- 在正确性假设建立和怀疑度排序阶段，利用历史案例加权指导。  
- 严格保护用户隐私，自动脱敏敏感信息，不记录页面完整文本内容。

---

### 核心原则

1. **轻量极简**  
   每个记忆文档 ≤ 200 行，只记录关键信息（调用堆栈、源头、假设、修复概要），不保存完整日志或源码内容，避免 token 膨胀。

2. **成功与失败分开存储**  
   - 成功修复 → `.debug/memory/<修复标题>.md`  
   - 失败分析 → `.debug/memory/FAIL-<修复标题>.md`  
   - 最终失败 → `.debug/memory/FAIL-FINAL-<修复标题>.md`（系统层重启后仍失败时使用）

3. **自动脱敏**  
   生成记忆文档时，AI 必须执行以下脱敏规则：
   - 字段名含 `password`, `secret`, `token`, `apiKey`, `authorization`, `private`, `credential` → 值替换为 `[REDACTED]`。
   - 完整页面文本内容（如 API 响应体、HTML 等）不得写入文档，只保留关键字段摘要。
   - 用户个人信息（邮箱、手机号、IP 地址）替换为 `[REDACTED]`。
   - 脱敏后 AI 需检查一次，确认无遗漏。

4. **文件名即索引**  
   文件名直接描述修复内容，使用英文或拼音，长度 3~10 词，例如 `Fix-getCart-null-check.md` 或 `订单结算优惠券空指针修复.md`。如果文件名冲突，追加 `-2`、`-3` 等后缀。

5. **检索优先**  
   分析新 Bug 时，AI 首先列出 `.debug/memory/` 目录下所有文件名，按当前 Bug 的关键词（异常类型、函数名、模块路径）进行模糊匹配。只读取最相关的 1~3 份文档。如果文件名无法判断相关性，则跳过，不读取。

---

### 成功修复记录格式

```markdown
# 修复记录：<标题>
**时间**：2026-05-11 14:23
**复杂度评估**：简单（得分 2）
**调用堆栈**：handleRequest → getCart → checkout → applyCoupon
**错误源头**：getCart 返回 null 且调用方未处理
**正确性假设**：getCart 对已登录用户应返回非 null Cart 对象
**修复方式**：
- 文件：src/app.js
- 变更：在 handleRequest 中增加 `if (!cart)` 提前返回
**修复结果**：成功。回归日志确认 null 路径被截断，不再触发下游异常。
```

---

### 失败分析记录格式

对于方向自疑或飞轮耗尽导致的失败，记录内容应更详细，包含方向质疑内容。

```markdown
# 失败分析：<标题>
**时间**：2026-05-11 16:45
**复杂度评估**：复杂（得分 7）
**调用堆栈**：handleRequest → getCart → checkout → applyCoupon
**飞轮轮次**：3 轮耗尽
**已尝试假设与验证**：
1. 假设：getCart 返回 null → 埋点验证：cart 正常
2. 假设：coupon.isValid() 返回 false → 埋点验证：返回 true
**方向质疑**：
- 上下文缺失或失真：缺少优惠券类型、用户等级信息。
- 正确性假设根因错误：可能真实契约涉及多条件组合。
- 修复路径误判：前两轮修复均未命中。
**建议方向**：向用户确认业务规则，重新建立假设。
```

对于系统层重启后仍失败的最终失败记录：

```markdown
# 最终失败分析：<标题>
**时间**：2026-05-11 17:20
**复杂度评估**：复杂（得分 8）
**调用堆栈**：涉及 5 个模块，跨服务调用
**分析历程**：3 轮飞轮 → 方向自疑 → 系统层重启 → 再次失败
**方向质疑**：
- 架构级缺陷：可能存在全局状态污染。
- 多 Bug 交织：可能有多个缺陷相互掩盖。
**最终建议**：拆分问题，引入分布式追踪，人工架构评审。
```

### 检索与复用流程

1. **列举文件名**：在新 Bug 的静态分析阶段，AI 使用工具列出 `.debug/memory/` 目录下的所有 `.md` 文件名。
2. **关键词提取**：从当前 Bug 的异常信息、函数名、模块路径中提取 2~5 个关键词。
3. **模糊匹配**：将关键词与文件名逐一比对匹配度。匹配度高的文件优先读取。
4. **分批读取**：最多读取 3 份文档内容。如果匹配的文件超过 3 个，按时间戳排序读取最新的 3 个。
5. **应用历史**：
   - 若匹配到成功案例，且调用链和异常类型高度相似，可直接参考其中的正确性假设和修复方式，并在复杂度评估的历史相似度维度中抵扣 `-2` 分。
   - 若匹配到失败案例，主动提示用户避免重蹈覆辙，且不给历史相似度减分。
6. **不询问用户**：整个过程由 AI 自主完成，不询问“是否读取记忆文件”。

---

### 文档生命周期

- **创建**：在 Mark Fixed 或方向自疑/最终建议后自动生成。
- **保留**：记忆文档持续存在于项目内，清理脚本 `cleanup-debug-blocks.js` 不会删除 `.debug/memory/` 目录。
- **手动清理**：用户可随时手动删除或编辑记忆文档，AI 不干预。
- **过期**：无自动过期机制。用户可根据项目需要定期清理。

---

### 与其它参考文档的协同

- **复杂度评估**：历史相似度维度依赖记忆库检索结果。  
- **方向自疑**：失败分析文档记录方向质疑内容，供后续避坑。  
- **交互流程**：Mark Fixed 或最终建议后调用本文档生成记忆。  
- **埋点与修复**：成功案例中的假设和修复方式可指导新 Bug 的分析和补丁设计。

---

**使用提示**：记忆库是 DebugFixer 的经验宝库。每次修复结束后，花一点时间回顾过程，生成一份准确的记忆文档。这不仅是记录，更是给未来的自己（或同项目其他使用者）提供的宝贵线索。始终保持脱敏意识，保护隐私是最高优先级。

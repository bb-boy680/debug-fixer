# 方向自疑

## 文档描述

多轮调试无实质进展时，继续猜不如停下来反思——是分析方向错了，还是问题根本不在代码层面？

本文档定义方向自疑的完整流程：何时触发、如何前置审查防止过早放弃、如何复盘、以及两个出口各自的处理方式。

本文档在第六步触发时调用。

## 为什么需要方向自疑

调试中最常见也最昂贵的错误是**在错误方向上钻得太深**。AI 可能一开始就忽略了某个关键假设、遗漏了调用链上被拦截器/中间件转发的节点、或者把症状当成了根因。方向自疑强制你停下来——退一步看看自己在做什么、是不是从一开始就偏了。

同时，并不是所有问题都是代码写错了——模块之间的接口约定可能根本不支持这个行为。方向自疑的出口 B 处理这种情况：承认代码层面追不到根因，向用户说清楚为什么，让用户拿着分析结论去调用 /plan。

## 触发条件

以下任一条件满足时，进入方向自疑：

| # | 条件 | 来源 |
|---|------|------|
| 1 | 用户纠正你的方向 ≥2 次 | 主动 |
| 2 | 用户描述与代码静态分析结果根本矛盾 | 主动 |
| 3 | 埋点日志调用链与用户复现步骤严重不一致 | 主动 |
| 4 | 同一假设被证据否定 ≥2 次 | 主动 |
| 5 | 首次修复失败后仍想在无新证据下继续改 | 主动 |
| 6 | 代码修改 ≥2 次但 BUG 仍在 | 主动 |
| 7 | 排查超过 5 个回合无实质进展 | 主动 |
| 8 | 连续两轮埋点未捕获偏差 | 被动（第三步触发） |
| 9 | 三轮埋点耗尽仍无法定位源头 | 被动（第三步触发） |

## 流程

触发条件满足后，按以下顺序执行。不做分类、不填模板——最困惑的时候只需要最简单的指令。

### 第一步：前置审查

在质疑方向之前，先确认不是差最后一轮埋点，或者只是首次修复失败但还没拿到新证据。任一项为"是"则暂缓质疑，追加埋点后继续第三步：

- [ ] 我最怀疑的那个节点，真的用埋点验证过了吗？
- [ ] 追加一轮埋点（≤2 处）是否可能直接锁定？
- [ ] 当前是不是还缺运行时证据，而不是方向已经被证伪？

两项均为"否" → 继续下一步。

### 第二步：回退

你改了几次都没修好，这些修改本身已经变成了干扰。继续往下走，你会分不清哪些是原始逻辑、哪些是你失败的尝试。

把你这次 debug 过程中改过的代码逐处还原，不要动用户其他改动。不要用 git——那会丢掉用户没提交的代码。埋点用 cleanup-debug-blocks.js 清理。

### 第三步：复盘

向用户交代三件事，用自由文本，不要求固定格式：

1. **假设与证据**：当前假设是什么？支撑它的证据和矛盾的证据分别是什么？
2. **排查范围**：是否太窄？是否一开始就排除了某个方向没再回头看过？
3. **进展**：经过了多少轮分析，卡在哪个节点？

如果这轮复盘确认了稳定的负向约束，先记进当前 session 记录；只有当同类负向约束在多个 session 里反复出现时，才升级成反模式记忆。

### 第四步：判断去向

基于复盘结果，判断走哪个出口。**不确定时默认走出口 A**——出口 B 是最后手段，不是捷径。

**出口 A：继续调试**

复盘后发现假设方向有误，推翻后可以重新来过。直接执行：

- 推翻被复盘中否定的假设，标记为负向约束
- 带上已排除的方向清单
- 重新进入第一步【多维分析】阶段——利用上一次的经验和负向约束，对 BUG 做新的理解和分析
- 不保留旧的中间结论——只保留负向约束和环境判定结论

**出口 B：设计问题**

只有在以下条件**全部满足**时才能走出口 B。这是硬门禁，缺一条就回出口 A：

1. 调用链上的**每一个**节点都经过了验证（埋点日志或静态代码确认），没有跳过任何节点
2. 每个节点的验证结论一致——各自独立正确，没有单点偏差
3. 复盘第 2 问（排查范围）确认没有遗漏方向——你确实排查了，不只是"觉得够了"

走出口 B 时，必须先列出调用链节点验证清单，证明条件 1 和 2 成立：

```
调用链验证清单（出口 B 专用）：
[ ] 节点 A — 验证方式：[埋点/静态代码] — 结论：[入参正确，输出正确]
[ ] 节点 B — 验证方式：[埋点/静态代码] — 结论：[入参正确，输出正确]
...
```

有任何一个节点填不出验证结论 → 不满足条件 1 → 走出口 A。

条件全部满足后，退出 debug-fixer，输出以下内容：

```
【无法通过代码修复定位根因】

经过 X 轮分析，调用链覆盖了以下节点：
- 节点 A（验证结果：入参正确，输出正确）
- 节点 B（验证结果：...）
- ...

为什么代码层面追不到根因：
[用 2-3 句话解释——是模块间接口约定问题？数据流设计缺陷？全局状态被多个入口同时修改？]

建议重构方向：
[从哪个接口/边界入手，调整什么设计]

可以调用 /plan 生成重构方案。
```

退出后 debug-fixer 结束。用户拿着这段分析去调 /plan。

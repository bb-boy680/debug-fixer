# 根因追溯指南

## 文档描述

本文档定义 debug-fixer 的根因追溯方法论：从异常表现出发，沿调用链或 DOM/CSS 继承链反向追溯，每一步对照正确性假设，找到数据或样式首次偏离预期的节点。

逻辑缺陷和视觉缺陷共用同一套追溯框架，差异仅在于链路载体不同（函数调用链 vs DOM/CSS 继承链）。

本文档承接【多维分析】输出的假设和调用链，产出根因定位结果供【源头修复】使用。当静态推理无法清晰展现数据流向时，转入 `instrumentation-guide.md` 的埋点二分法。

---

## 核心原则

1. **上游优先**：永远从异常表现处向上追，不凭直觉跳转到"看起来可疑"的远端节点。
2. **逐层验证**：每一跳必须对照正确性假设，确认入参/样式是否符合预期，禁止跳过中间层。
3. **首次偏离即源头**：数据/样式在哪一跳首次偏离预期，那一跳就是源头。
4. **症状不是根因**：错误抛出的位置 ≠ 错误产生的位置。崩溃处的代码可能只是被喂了异常数据。
5. **链路完整，不跳边界**：异步调用、中间件、管道、拦截器、跨文件/跨包调用都必须纳入追溯链，每一层都算一跳。

---

## 禁止行为

- **禁止在异常表现处直接修复**：不向上追溯数据来源就修改崩溃位置的代码，是修症状不是修根因。
- **禁止跳过中间层**：即使某层"看起来很简单"（如纯转发函数、薄 wrapper），也必须纳入追溯链。
- **禁止静态推理不足时强行修复**：调用链无法通过代码阅读理清时，必须转入埋点二分法收集运行时证据，不得凭猜测修代码。
- **禁止用 `!important` 覆盖视觉问题**：视觉修复必须改根源规则，不是强制覆盖症状。
- **禁止跨异步边界中断追溯**：`await`、`.then()`、`setTimeout`、消息队列等异步节点是链路的一环，不能跳过。

---

## 追溯流程

### 单次追溯

```
异常表现点
    ↓ ① 观察症状：确定异常位置与表现
    ↓ ② 制定当前节点的正确性假设：入参应该是什么？输出应该是什么？
    ↓ ③ 检查实际入参/样式是否符合节点假设
    ├─ 入参/样式符合假设，但输出偏离 → 源头是本地逻辑 → 停止
    └─ 入参/样式已偏离假设 → 上游传入
            ↓ ④ 沿链路向上跳一层（调用方 / 父容器）
            ↓ ⑤ 回到 ②，为上游节点重新制定假设，直到找到首次偏离点
```

### 源头判定

| 情况 | 判定 | 行动 |
|------|------|------|
| 入口参数/样式符合假设，但输出/渲染偏离 | 源头在**本地** | 停止追溯，进入【源头修复】 |
| 入口参数/样式已偏离假设 | 来自**上游** | 继续向上追溯 |
| 自身正确，但下游/子元素异常 | 检查当前节点副作用 | 向下游确认，同时检查当前节点的中间件/管道 |
| 视觉：自身 CSS 规则直接导致偏差 | 源头在本地 | 修复 CSS 规则 |
| 视觉：受父容器影响（裁剪、定位上下文） | 来自上游 | 向上追溯父容器 |
| 视觉：JS 动态注入的值错误 | 转入逻辑链路 | 按逻辑链路追溯 JS 代码 |

## 逻辑链路

从异常函数开始，沿调用栈反向追溯，每一跳检查入参和输出是否符合假设。

### 链路覆盖清单

- 函数调用、方法调用、路由/中间件链
- 导入/导出关系、跨文件/跨包调用
- 异步边界（`await`、`.then()`、回调、`setTimeout`、消息队列）视为链上节点，不断裂
- 中间件、管道、拦截器、装饰器必须纳入追溯

### 框架注意点

- **Express/Koa**：按中间件注册顺序反向推导
- **React/Vue**：关注组件层级、props 传递、状态提升路径
- **异步任务**：记录触发源（消息队列、定时器），跨异步边界持续向上

### 追溯受阻

以下情况静态推理无法继续时，转入埋点二分法（见 `instrumentation-guide.md`）：

- 调用链涉及动态派发（如策略模式、依赖注入）、静态代码无法确定实际调用方
- 跨进程 / 跨服务边界、调用链不完整
- 数据流经过多层变换后无法追踪来源

## 视觉链路

从异常元素开始，沿 DOM 树与 CSS 继承反向追溯。

### 追溯步骤

1. 检查元素自身 `computedStyles` 是否符合视觉假设
2. 自身样式正确但布局异常 → 向上检查父容器/祖先的 CSS
3. 重点关注：
   - 父容器的 `overflow`、`position`、`display`、`flex`/`grid`
   - 媒体查询是否在不同视口下覆盖样式
   - CSS 优先级：classList 和样式来源判断是否被更高优先级规则覆盖
4. 样式由 JS 动态设置 → 转入逻辑链路继续追溯

### 视觉 Bug 分类速查

| 症状 | 重点检查 |
|------|----------|
| 位置错位 | `position`、`flex`/`grid`、盒模型 |
| 点击无响应 | `z-index` 堆叠、`pointer-events`、透明遮挡层 |
| 不显示/意外显示 | `display`、`visibility`、`opacity`、条件渲染逻辑 |
| 响应式异常 | 媒体查询断点、`viewport` 设置、`rem`/`vw` 使用 |
| 弹窗被遮挡 | `z-index` 堆叠上下文、父容器 `overflow: hidden` |
| 文本截断/溢出 | `white-space`、`overflow`、`text-overflow`、容器宽度 |
| 样式不生效 | 选择器优先级冲突、`!important` 滥用、样式表加载顺序 |
| 暗色模式错误 | CSS 变量继承、`prefers-color-scheme`、`color-scheme` 属性 |
| hover/focus 无反应 | 伪类样式、选择器优先级、`pointer-events` 禁用 |
| 动画不流畅 | `transition`/`animation` 时序、重排/重绘、JS 频繁操作样式 |

### 视觉修复铁律

1. 改根源规则，不覆写症状（不用 `!important` 强制覆盖）
2. 修复不破坏其他断点
3. 理解优先级，沿用原有选择器写法
4. 用 CSS 类名切换而非 JS 频繁操作样式

## 偏差传播输出

确定源头后，输出完整传播路径：

**逻辑示例**：
```
【偏差传播】
getCart 返回 null → checkout 收到 cart=null → applyCoupon 访问 null.discount → TypeError
【修复】修改 getCart 确保返回空对象而非 null（源头修复）
```

**视觉示例**：
```
【偏差传播】
.sidebar-wrapper overflow:hidden + width:0 → .sidebar 被裁剪不可见 → 点击后侧栏不显示
【修复】修改 .sidebar-wrapper 在移动端媒体查询中的 width 值（源头修复）
```

## 每步对照

追溯的每一步都必须执行以下检查，缺一不可：

| 步骤 | 检查项 | 不通过的后续动作 |
|------|--------|------------------|
| 当前节点入参/样式 | 是否与正确性假设一致？ | 不一致 → 继续向上追溯 |
| 当前节点内部逻辑 | 入参正确时，输出是否偏离？ | 偏离 → 源头在本地，停止追溯 |
| 当前节点上游来源 | 上游节点是否可确定？ | 不可确定 → 转入埋点二分法 |
| 当前节点假设验证 | 假设被证实还是证伪？ | 高置信度假设被违背 → 优先修复；多低置信度假设被证伪 → 触发方向自疑 |

## 与其它参考文档的协同

- 埋点体系：`instrumentation-guide.md` — 当调用链节点动态派发（DI 容器、策略模式）、数据流经多层变换无法肉眼追踪、或追溯超过 5 层仍不明确时，转入埋点二分法收集运行时数据，之后回到本文件继续追溯
- 方向自疑：`direction-doubt.md` — 多轮追溯无法定位源头，或埋点证据与静态推理矛盾时触发
- 分层重启：`restart-strategy.md` — 系统层重启后重新执行本文件

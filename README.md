SKILL 说明
这个 SKILL 是为了精准定位 BUG 并对问题源头进行根本修复，它包含以下的手段:

【你的能力】
- 多记忆缓存和读取
- 静态代码推理：根据静态代码进行完整分析、重建完整的调用栈
- 视觉化分析：不止能推理逻辑代码、还能根据视觉分析样式问题
- 问题假设：可以根据用户反馈的问题、提出自己产生这个问题的假设
- 日志埋点：通过埋点的手段在运行时收集直接证据、更加快速地定位问题
- 自我怀疑：当对一个问题进行反复修复和分析时、可能进入了修复路线的循环、这是很严重的问题、要立即进入自我怀疑
- 方向重启：如果按照一个方向进行分析没有结果、根据【方向自疑】看情况进行重启、并立即回退修改过的代码


【交叉验证】

定位到根本原因后、不直接进入修复。必须经过交叉验证门禁。

交叉验证 = 至少两个独立信息源同时指向同一个根因

信息源维度:
- 静态代码推理: 调用链分析、类型推断、逻辑断点
- 记忆匹配: 历史上类似 BUG 的根因和修复方式
- 运行时证据: 埋点日志、错误堆栈、网络请求
- 视觉证据: 截图对比、布局分析、样式断层
- 用户确认: 通过 question 工具向用户确认的行为观察

交叉验证规则:
- 任意两个维度同时指向同一根因 → 通过门禁、进入【源头修复】
- 只有一个维度有证据 → 证据不足、进入【埋点分析】
- 两个维度互相矛盾 → 进入【方向自疑】、重建假设


【多维分析】

用户启用 debug-fixer 时的第一阶段分析，流程为:

1. 获取记忆：探索记忆库查看是否有相似 BUG、积累之前的修复经验和踩过的坑
2. 重建调用链：根据用户问题在代码中找到完整调用回路、包括调用堆栈和视觉化样式链
3. 生成假设并向用户确认：根据 BUG 表现和调用链提出多个可能假设，通过 question 工具以多选方式向用户确认（根因可能是多个因素叠加）

例如，用户报告"登录后没有跳转到首页":

加密搜索记忆库，发现历史案例"Token 未设置导致重定向回登录页"。重建调用链: login() → setToken() → router.push('/home') → authGuard 拦截。
然后通过 question 工具以多选列出假设请用户确认、例如：
```
用户反馈登陆后并没有跳转到首页、我需要向用户确认我的假设方向（这个是标题）
options(多选):
   - 登录接口报错，请求未成功
   - 路由跳转未生效或缺少跳转逻辑
   - Token 未正确设置，被 authGuard 重定向
```

用户确认后（可能选中一个或多个），进入交叉验证门禁:

静态代码 + 记忆匹配 同时指向同一根因 → 门禁通过 → 进入【源头修复】
静态代码 + 用户确认 同时指向同一根因 → 门禁通过 → 进入【源头修复】

只有静态代码一个维度有证据 → 证据不足 → 进入【埋点分析】
记忆匹配指向根因但静态代码不支撑 → 证据不足 → 进入【埋点分析】

两个维度互相矛盾 → 进入【方向自疑】→ 回到【多维分析】重新构建假设


【埋点分析】

当前假设证据不足时、通过运行时日志收集直接证据。

1. 根据当前假设确定埋点位置（调用链的关键分叉点）
2. 运行 BUG 场景、收集运行时日志
3. 拿到日志后进入证据分析:

   静态代码 + 运行时证据 同时指向同一根因
     → 交叉验证通过 → 进入【源头修复】

   运行时证据否定当前假设
     → 假设被证伪 → 根据新证据生成新假设 → 回到步骤 1 重新埋点

   运行时证据既不证实也不否定（模糊/无关）
     → 埋点位置不对 → 调整埋点 → 回到步骤 2

   运行时证据与静态代码推理矛盾
     → 理解模型错误 → 进入【方向自疑】→ 回退修改 → 重建假设


【源头修复】

交叉验证通过后、对根因进行一次性修复。这是唯一的修复阶段。

多维分析和埋点分析两条路径最终汇聚于此。区别仅在于到达这里的证据标准不同:
- 多维分析路径: 静态代码 + 记忆/用户/视觉 → 修复
- 埋点分析路径: 静态代码 + 运行时数据 → 修复

修复前确认:
- 至少两个独立信息源同时指向同一根因
- 修复目标明确：只改根因、不动无关代码

修复成功:
- 代码改动符合交叉验证指向的根因
- 用户验证 BUG 消失（不是"代码看起来对了"）
- 完成后生成记忆文档 → 整个流程结束

修复失败:
- 绝对不要尝试再次直接修复
- 失败意味着交叉验证的证据可能指向了错误方向
- 进入【埋点分析】时需携带失败信息（改了哪里、为什么没生效）作为新一轮假设的输入


【方向自疑】

以下任一条件触发、强制进入自疑:

- 同一假设被证据否定 ≥ 2 次
- 代码修改 ≥ 3 次但 BUG 仍在
- 证据维度互相矛盾（埋点数据与代码推理不一致）
- 排查超过 5 个回合无实质性进展

自疑流程:
1. 暂停所有修改
2. 复盘: 当前假设是什么、哪些证据支撑、哪些证据矛盾
3. 检查: 是否一开始就忽视了某个真相？排查范围是否太窄？
4. 决定: 继续当前方向 or 进入【方向重启】


【方向重启】

决定方向错误后的重置流程:

1. 回退本次 BUG 过程中所有修改过的代码
2. 回到【多维分析】重新构建调用链
3. 重建假设时必须明确引用"之前为什么走错了"作为负向约束、避免同一 session 内原地打转

【日志埋点】

生成会话 ID:`debug_YYYYMMDD_HHmmss_随机4位`、作为日志文件前缀

统一埋点入口：
- 客户端使用 http、调用日志服务保存到本地文件
    需要调用 http 服务、使用后台运行
- 服务端使用文件写入的能力写入到本地文件

环境缓存:
- 检索当前需要埋点的代码环境、并缓存到 `.debug/config.yaml`文件里面
- 下次需要埋点时、通过 Glob 工具直接读取缓存文件、无需重新检索、能节省大量 Token

埋点代码的清理触发条件和完整清理链详见【用户交互】。

【用户交互】

每次对话回合结束前、AI 工具需要调用 `question` 工具进行交互、引导用户进去下一个的流程：

- **Proceed**：Bug 未修复，AI 智能选择后续操作（追加埋点、调整假设、启动方向自疑等）
- **Mark Fixed**：Bug 已修复，执行清理链：关闭后台日志服务 → 删除日志文件 → 清理埋点代码 → 生成记忆文档

完整流程:

用户报告 BUG
    ↓
【多维分析】: 记忆检索 + 重建调用链 + 生成假设
    ↓
交叉验证门禁: 至少两个维度指向同一根因?
    ├─ 是 → 【源头修复】
    │         ↓
    │    【用户交互】Proceed / Mark Fixed
    │         ├─ Proceed → 转【埋点分析】（携带失败信息）
    │         └─ Mark Fixed → 清理链: 关闭日志服务 → 删除日志文件 → 清理埋点代码 → 生成记忆 → 结束
    │
    ├─ 证据不足 → 【埋点分析】
    │                ↓
    │          证据分析
    │           ├─ 通过 → 【源头修复】
    │           ├─ 否定 → 新假设 → 重新埋点
    │           └─ 矛盾 → 【方向自疑】
    │                       ↓
    └─ 证据矛盾 → 【方向自疑】
                      ↓
                 【方向重启】: 回退代码 + 清理埋点代码 → 回到【多维分析】（携带负向约束）
